# 品質レビュー（/quality-review）

#56 の品質チェックと、そのあとの修正（#57〜#75）で使った観点をまとめたもの。
レビューのたびに同じ観点で見られるようにし、見落としや判断のぶれを減らす。

## 進め方

1. **範囲を決める**: 指定がなければ、画面（`frontend/`）とサーバー（`backend/`）の全体と、`docs/` の要件定義書・機能仕様書・画面設計書を見る。PR のレビューなら、その差分と関係する資料だけを見る
2. **自動チェックを流す**（「自動チェック」の節）。失敗したものは、そのまま指摘に入れる
3. **観点ごとに読む**（「観点」の節）。資料は先に読み、実装と照らし合わせる
4. **指摘をまとめる**（「報告のしかた」の節）
5. **直す・Issue にする**: すぐ直すものも残すものも、CLAUDE.md の Git 運用ルールどおり Issue → ブランチ → PR で進める。直すのはユーザーの確認を得てから

## 自動チェック

すべて、指摘が1つでもあれば失敗する設定にしてある。PR では GitHub Actions（`.github/workflows/ci.yml`）も同じものを動かし、どちらも通らないと main にマージできない（Ruleset `protect-main` の必須チェック）。

| 対象 | コマンド | 中身 |
|---|---|---|
| 画面 | `cd frontend && npm run lint` | oxlint（設定は `.oxlintrc.json`。React のフックの決まり・アクセシビリティ・import など） |
| 画面 | `cd frontend && npm test` | Vitest + React Testing Library |
| 画面 | `cd frontend && npm run build` | 型チェックとビルド |
| サーバー | `cd backend && ./gradlew check` | Checkstyle（`config/checkstyle/checkstyle.xml`）・Error Prone（コンパイルのたび）・テスト（Testcontainers。Docker が必要） |

lint の指摘を `oxlint-disable` で黙らせるのは、ほかに方法がないときだけにし、理由をコメントで残す（例: Firefox は `<button>` をドラッグできないので、カードは `div role="button"` にしている）。

## 観点

### 1. 資料と実装の食い違い

`docs/requirements.md`（要件定義書）・`docs/features.md`（機能仕様書）・`docs/screens.md`（画面設計書）と実装を照らし合わせる。
食い違いを見つけたら、**どちらを正とするか**を次の基準で決め、指摘に書く。

| 正とする方 | どんなとき | 例 |
|---|---|---|
| **設計書（実装を直す）** | お客さまと合意した範囲（「対象外」「今後の追加候補」など）にかかわる。設計者が意図して決めた見た目・動き。モックや今の公開版と実装がずれている | 優先度の色分けは「対象外」だったのに実装していた（#72）。「優先度: 高」と文字で出す設計だったのにバッジに「高」だけを出していた（#72）。720px 以下で縦の設計が、Tailwind の書き方の都合で 720px 未満になっていた（#74） |
| **実装（資料を直す）** | 資料に書かれていない細かい動き。実装したほうが使いやすく、合意の範囲を変えない | 登録の返事を待つ間カードを薄くする、読み込みの失敗に「再読み込み」を出す、Space キーでもカードを開ける（#56・#68） |

- 迷ったら、どちらかに決めつけずユーザーに確認する。要件定義書（お客さまに出す資料）を変えるときは、改訂履歴に版数と理由を書く
- 資料を直したら、要件定義書・機能仕様書・画面設計書の3つで記述がそろっているかも確かめる（1つだけ直して残りが古いままになりやすい）
- CLAUDE.md と AGENTS.md は同じ内容にそろえる

### 2. React の決まった書き方（`frontend/`）

- **effect の中で state を同期的に変えない**: 読み込みの開始で `setState("loading")` を effect の中から呼ばず、イベントの側で変えるか、Promise の結果で変える（`Board.tsx` の `load`）
- **表示から求められる値は state に持たない**: 開いているカードは id だけを持ち、カードの中身は描画のたびにボードから求める。「state を合わせるための effect」は作らない
- **古い state をもとに書き換えない**: 続けて操作したときに前の操作が消えないよう、`setState(prev => …)` の形で書く（#63）
- **effect の後片付け**: `addEventListener` には `removeEventListener`、`setTimeout` には `clearTimeout` を対にする。付けた class も外す（`App.tsx` の背景写真）
- **配列を直接変えない**: `sort()` ではなく `toSorted()` を使う
- **色は `styles.css` の `@theme` に登録したものを使う**: クラスに色を直接書かない（#67）。ダークモードの上書きも忘れない
- **エラーの扱い**: 操作は先に画面を書き換え、保存に失敗したらエラーの帯を出して読み込み直す（CLAUDE.md の「アーキテクチャ」）。この流れから外れた操作がないか

### 3. Spring Boot の決まった書き方（`backend/`）

- **層を分ける**: controller は入出力だけ、処理は service、DB は repository。controller から repository を直接呼ばない
- **入力の確認**: DTO に Bean Validation（`@NotBlank` など）を付け、`@Valid` で確かめる。画面と同じルールをサーバーでも確かめる（画面設計書「3. 入力のルール」）
- **決まった値は型で表す**: 優先度のように値が決まっているものは String ではなく enum で持つ（#62）
- **エラーの形をそろえる**: 想定外のエラーや存在しない API でも、決めた形（`{ "error": "…" }`）で返す（#60）
- **同時の操作**: 並び順などが重ならないか。必要なら楽観ロック（`@Version`）を使う（#64）
- **テスト**: `@SpringBootTest` には `@Import(TestcontainersConfiguration.class)` を付け、本番と同じ PostgreSQL 18 で確かめる。コントローラーのテストは、ログイン・CSRF のチェック（Spring Security）を通した状態で行う（#58）
- **運用**: ヘルスチェックは Actuator（`/actuator/health`）を使う（#65）

### 4. セキュリティ

- ログインが必要な API が、ログインなしで呼べないか（401 になるか）
- `POST`・`PATCH`・`DELETE` が CSRF トークンなしで通らないか（403 になるか）
- パスワードの総当たりへの対策があるか（#61）
- 秘密の値（パスワード・接続先）がコードやコミットに入っていないか。環境変数（`APP_PASSWORD`・`DB_*`）で渡しているか
- ユーザーの入力を `innerHTML`（React では `dangerouslySetInnerHTML`）で差し込んでいないか
- 入力の長さに上限がないことで困らないか（#66。上限はお客さまと決める）

### 5. アクセシビリティ

- **キーボードだけで全部の操作ができるか**: カードは Tab で選んで Enter・Space で開ける。詳細画面は Esc で閉じる
- **色だけで区別していないか**: 優先度は「優先度: 高」と文字で出す（要件定義書 5.5）
- **意味に合った要素を使う**: まとまりには `fieldset` と `legend`、押せるものは `button`。やむをえず `role` で代えるときは理由を残す
- ボタンの中にボタンを入れない（カードの「×」は、開く部分の隣に置く）

### 6. 見た目の境目・細かい落とし穴

- **Tailwind の `max-[N]` は「N 未満」**: 設計書が「720px 以下」なら `max-[721px]` と書く（#74）。ビルドした CSS（`frontend/dist/assets/*.css`）の `@media` で実際の条件を確かめる
- 画面の文言（日本語）が、画面設計書の文言と一字一句そろっているか（「進行中」「作業中」のような揺れ）

## 報告のしかた

指摘は重い順に並べ、1つずつ次の形で書く。

| 項目 | 書くこと |
|---|---|
| 重さ | **高**（不具合・セキュリティ・合意した範囲とのずれ）／**中**（決まった書き方から外れていて、いずれ不具合になりうる）／**低**（読みやすさ・細かい揺れ） |
| 場所 | `frontend/src/components/Board.tsx:247` のようにファイルと行 |
| 内容 | 何が問題か。資料との食い違いなら、資料のどこと食い違うか |
| 直し方 | どう直すか。資料と実装のどちらを正とするか（観点 1 の基準） |

- 重さ「高」と、すぐ直せるものは、その場で直してよいかユーザーに確認する
- 残すものは、1つの指摘を1つの Issue にする（ラベルは `bug`・`enhancement`・`documentation`）。#58〜#67 がその例
- 自動チェックの結果（通った・失敗した）は、そのまま書く。失敗を隠さない
